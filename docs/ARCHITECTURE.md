# Architecture

## Layering

The backend follows MVC layering: routes validate and dispatch requests to controllers; controllers coordinate services without containing business logic; services implement workflows and business rules; repositories own persistence access. Only repositories import Prisma. Serializer functions shape all responses, and centralized error handling returns the documented error envelope. The frontend is a Next.js App Router application using strict TypeScript and API-mirroring types.

The backend uses Prisma ORM 7.10.0 with PostgreSQL and the `@prisma/adapter-pg` driver adapter. Runtime connections use Supabase's pooled `DATABASE_URL`; Prisma CLI migration commands use `DIRECT_URL`. The JavaScript ESM backend uses Prisma's `prisma-client-js` generator because the current `prisma-client` generator emits TypeScript source. The JS generator is deprecated in Prisma 7; it is retained here to honor the project's no-TypeScript backend constraint. Prisma Client is generated by `prisma generate` and imported from `@prisma/client`. The setup follows the [Prisma 7 generator documentation](https://www.prisma.io/docs/orm/v7/prisma-schema/overview/generators), [Prisma Client ESM setup](https://www.prisma.io/docs/orm/v7/prisma-client/setup-and-configuration/introduction), [Prisma config reference](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference), [PostgreSQL driver-adapter documentation](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql), and [Supabase connection guidance](https://www.prisma.io/docs/orm/overview/databases/supabase).

`GET /health` follows the route -> controller -> service -> repository path and runs `SELECT 1` through Prisma. Request logs use Pino with a generated request ID. Errors are returned through the centralized middleware without stack traces or raw database error messages.

## Authentication and assessment authorization

Authentication endpoints are `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, and `POST /api/v1/auth/logout`; the current-user endpoint is available at `GET /auth/me` and `GET /api/v1/auth/me`. Passwords are bcrypt-hashed. A one-hour JWT is stored in an HTTP-only, `SameSite=Lax` cookie; `COOKIE_SECURE=true` enables the Secure attribute for HTTPS. Requests may instead provide the JWT as a Bearer token. Login attempts are limited per client IP, and login successes and failures create `AuditEvent` rows without storing credentials or submitted email addresses. Both unknown accounts and incorrect passwords receive the same `Invalid credentials` response.

`requireAuth` verifies the token and attaches only the public user fields (`id`, `email`, and `name`) as `req.user`. Assessment queries must constrain ownership in the repository query itself (for example, `where: { id: assessmentId, userId: req.user.id }`). Missing and non-owned assessments both return 404 to avoid revealing another user's records.

## Documents, segmentation, and citations

Each immutable guideline or application document version is segmented into addressable text segments. Segment IDs use stable labels such as `S1`, `S2`, and so on within that document version. Each segment stores its text and source offsets (start inclusive, end exclusive) into the version's extracted text. The segmenter splits blank-line-delimited paragraphs, Markdown headings, and individual list items, preserves source offsets, and rejects content exceeding `MAX_DOCUMENT_CHARS` (200,000 characters). Content hashes use SHA-256 after BOM removal, line-ending normalization, Unicode NFC normalization, and trimming.

Assessment, document-version, and supporting-document APIs require authentication. Assessment ownership is included in database query predicates, and non-owned resources return 404. Document uploads accept JSON text or `.txt`/`.md` multipart files. New versions, current-version pointer changes, and audit events are committed together; matching the current version's normalized content hash returns the existing version without modifying immutable content.

AI mappings cite a document version, segment ID, and supporting excerpt. Code resolves the cited segment against that exact immutable version and verifies that the cited excerpt matches text in the stored segment. A citation that cannot be resolved or verified is unverified and never counts as satisfied.

Backend citation verification is exact after case/whitespace normalization and straightening typographic quotes and dashes. Quotes shorter than 12 normalized characters, unknown segment IDs, and non-matching text are unverified; there is no fuzzy matching. Each saved evidence item records its own `verified` flag, while a mapping's `allVerified` is false for empty evidence or any unverified item. Requirement sources and unsupported-claim quotes are independently verified against their corresponding immutable version.

## AI workflow

The AI workflow has three steps:

1. **Extract requirements:** read the guideline and return structured requirements, including their text, mandatory-versus-recommended classification, and source citations.
2. **Map application content:** associate application evidence with each requirement, return structured support status and citations, and flag evidence that is missing, weak, or ambiguous.
3. **Find unsupported claims and questions:** identify application claims unsupported by supplied evidence and generate clarification questions for gaps or ambiguity.

Every AI response is JSON validated against a zod runtime schema. AI output is advisory; it cannot trigger actions or decide completion. AI output and human review decisions are stored separately, and review never overwrites the original AI result.

The provider contract is `completeJson({ system, user })`, returning response text, token usage, provider name, and model. The OpenAI-compatible provider requests JSON mode and retries transport failures once; structured output validation retries once with concise schema paths. If a live provider is configured and both transport attempts fail, the deterministic heuristic provider runs and the analysis metadata identifies the provider as `heuristic-fallback` so the UI can disclose that the AI was unavailable. Invalid model output after its validation retry raises `AI_OUTPUT_INVALID` rather than silently switching to heuristic results. `LLM_PROVIDER=heuristic` explicitly selects the offline deterministic provider.

`POST /assessments/:id/analysis` (also under `/api/v1`) creates a `RUNNING` `AnalysisRun` against the assessment's current immutable versions, with an assessment-scoped database lock preventing concurrent runs. It persists verified requirements, mappings, questions, and unsupported claims, then marks the run complete in one transaction. Failed executions are marked `FAILED` with a user-safe message; run start, completion, and failure each create an audit event. `GET /assessments/:id/analysis/latest` returns the latest completed analysis with review fields, and `GET /assessments/:id/analysis/runs` returns the owner's run history. Mapping citations are retained even when verification fails; deterministic scoring excludes unsupported AI evidence.

All prompts are versioned and label guideline and application content as untrusted data. The heuristic pipeline extracts modal-language requirements, maps by deterministic keyword overlap thresholds while excluding clearly negated evidence sentences, raises questions for unsupported mandatory requirements, and flags numeric/outcome claims. Its result is a clearly labeled fallback suggestion, not an AI or eligibility decision.

## Scoring and review

For each mapping, determine effective status as follows:

- `REJECTED` => `MISSING`
- `CORRECTED` => `reviewerStatus`
- `CONFIRMED` or `PENDING` => `aiStatus`

A mapping is satisfied only when its effective status is `SUPPORTED` and either it was reviewer-corrected or all of its evidence citations have been verified. Thus, unverified AI evidence cannot satisfy a requirement; a reviewer-corrected mapping is evaluated using the reviewer's status.

Completion is calculated by pure deterministic functions, never by the AI. Show AI-suggested counts/scores separately from reviewer-confirmed counts/scores. Report mandatory requirements separately from recommended requirements so recommendations do not obscure mandatory completeness. Determine a requirement's level using `levelOverride ?? aiLevel`.

The reviewed completeness summary is based on human review decisions plus deterministic scoring. It must include the disclaimer that the tool does not make an authoritative legal or funding-eligibility decision.

## Versioning and staleness

Document versions are immutable. A new guideline or application upload creates a new `DocumentVersion`; it does not mutate an existing version. An assessment is stale when the latest run's `guidelineVersionId` or `applicationVersionId` differs from the assessment's current guideline or application version ID.

## Data model

- **User:** user identity and ownership scope.
- **Assessment:** a review workspace, references its current guideline and application versions, and tracks assessment-level state.
- **DocumentVersion:** immutable content and metadata for a specific guideline or application version.
- **SupportingDocument:** metadata for an optional supporting document and its association with an assessment.
- **AnalysisRun:** one execution of the three-step AI workflow, linked to the exact guideline and application versions used.
- **Requirement:** a structured requirement extracted from a guideline, including mandatory/recommended classification and source citation.
- **Mapping:** AI-suggested relationship between a requirement and application evidence, with citations and separately stored human review decision.
- **ClarificationQuestion:** a question generated to resolve missing, weak, or ambiguous evidence.
- **UnsupportedClaim:** an application claim identified as lacking support in supplied evidence.
- **ReviewSummary:** the reviewed completeness summary and deterministic counts for the applicable assessment/run.
- **AuditEvent:** a record of relevant assessment, version, analysis, and review actions.
